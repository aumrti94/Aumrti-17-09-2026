# Known bug register

**Created:** 2026-09-11, as Phase 0 item 5 of [PHASED_TEST_PLAN.md](PHASED_TEST_PLAN.md).
**Rule (R2):** a test for an unfixed bug is written and committed in the phase that found it,
marked `it.skip` with the `KNOWN-BUG-` id in the skip reason, and never left red. Every `it.skip`
in the repo must resolve to a row in this table. CI `main` is never red.

**Severity (R1):** S1 patient safety / cross-tenant PHI leak / wrong money on a real invoice —
blocks the gate, no waiver. S2 silent wrong result in the surface under test — blocks unless
waived in writing. S3 correct behaviour, poor ergonomics or out of scope — logged, carried
forward. S4 harness problem — fix inline, never logged here.

## Numbering

- **001–008** — the eight defects enumerated in
  [TEST_STRATEGY_RECOMMENDATION.md](TEST_STRATEGY_RECOMMENDATION.md) §"Correction 1". Their
  defining property: **every one is silent.** Not one is a crash, an error, or a failed
  operation, so a journey test asserting "the workflow ran without error" passes on all eight.
  That is why §5 of the plan requires assertions on resulting state.
- **009–010** — deliberately unused. Reserved so the numbered series can absorb another
  pre-existing defect without renumbering anything already referenced from a test.
- **Correction, 2026-09-13**: several Phase 6 entries (KNOWN-BUG-172, -179, -181, -194, and the
  `dunning-processor`/`register-hospital` write-ups) described `.functions.invoke(...).catch()`
  as sharing the same "thenable but no real `.catch()`" defect as `.from().insert()`/`.update()`/
  `.rpc()`. **That specific claim is wrong** — confirmed empirically (`sb.functions.invoke(...)
  instanceof Promise` is `true`, with a genuine working `.catch()`), unlike `PostgrestBuilder`
  (`.from()`/`.rpc()` chains), which really does lack one. Where a fix touched an
  `invoke().catch()` call specifically, the replacement (explicit `try/await/catch` with the
  error checked and logged, instead of silently swallowed) is still a real improvement — the
  regression tests recorded against those entries verified genuine before/after behaviour
  differences — but the observed crash, where one was independently reproduced, came from an
  adjacent `.insert()`/`.update()`/`.rpc()` call in the same function, not the `invoke()` line
  itself. Left the historical entries as originally written rather than rewriting each one;
  applying the corrected understanding going forward.
- **Methodology note, 2026-09-13**: `purge-orphaned-users` deletes any orphaned `auth.users` row
  platform-wide, with no hospital scoping — and several other test files in this same suite
  (`register-hospital`, `setup-hospital`, `create-staff-login`, `admin-impersonate-start`,
  `abdm-abha-create`) briefly create an `auth.users` row before linking it to
  `public.users`/`aumrti_admins`. Running the real deletion path as part of the routine
  parallel suite is not safe: it was caught live non-deterministically failing
  `register-hospital.test.ts` by deleting its in-flight fixture out from under it. No permanent
  damage resulted (every Tier-0 seed account and all other fixtures were confirmed intact
  afterward), but `e2e/edge-functions/purge-orphaned-users.test.ts` now exercises only the two
  auth-gate checks (which reject before any query runs) in the standard suite; the deletion
  path itself was independently verified twice by running that file alone, with no other file
  executing concurrently — re-run it manually the same way if that function's logic changes,
  rather than restoring it to the parallel suite.
- **Audit note, 2026-09-13**: a Phase 0–6 retrospective (prompted by a direct question about
  whether any phase's exit gate was actually met) found that the "Target" column on this table is
  not self-enforcing — an entry can carry a target phase that has since been declared complete
  without ever being fixed, and nothing flags that automatically. Confirmed concretely:
  **KNOWN-BUG-107** (S3, drug-interaction dedup is case-sensitive, target "Phase 2") and
  **KNOWN-BUG-124** (S3, `_shared/phi-redactor.ts`'s pattern list still names two columns that
  were dropped in the KNOWN-BUG-121 recovery and is missing the two real replacement columns,
  target "Phase 5") were both still exactly as originally described, un-actioned, though their
  target phases were long past — **both fixed 2026-09-14, immediately after this audit, see
  Resolved below.** **KNOWN-BUG-148/149/153/157** (all S2, frontend settings screens
  whose controls have no runtime consumer, target "Phase 6") were not touched by this session's
  actual Phase 6 work, which scoped to edge-function auth/entitlement/audit plumbing — none of the
  four is a backend/edge-function fix, so none was in scope for what Phase 6 actually built,
  despite the register's own target column implying it should have closed here — re-targeted to
  Phase 9, not fixed. **KNOWN-BUG-127**
  was found to be an exact duplicate of KNOWN-BUG-188 (same file, same defect, fixed this phase)
  and has been moved to Resolved with a cross-reference rather than left as a second open row for
  an already-fixed bug. The four Phase-6-targeted items still open should be explicitly
  re-scoped (to Phase 9/10, or picked up now) rather than left with a target phase that has
  already passed.
- **011** — dual bill status vocabularies, named explicitly by D3.
- **100+** — found by the test suite itself.

## Observations that are not bugs

Recorded because each looks like a defect at a glance, and a future reader who "fixes" one would
make the product worse. Each has a pinning test.

| Surface | Behaviour | Why it stays |
|---|---|---|
| `src/lib/abdm-validators.ts` | A well-formed ABHA/Aadhaar that belongs to nobody **passes** | Format validation, not existence verification. A checksum or registry call here would reject legitimate identifiers offline and block registration at the desk. Existence is the ABDM gateway's job (Phase 6). |
| `src/lib/clinicalCalculators.ts` (CHA₂DS₂-VASc) | Risk table is non-monotonic — 9.8% at 6, 9.6% at 7, 6.7% at 8 | Lip 2010 reports exactly these figures. Smoothing the curve would fabricate data. |
| `src/lib/clinicalCalculators.ts` (BMI) | 72.2 kg at 170 cm displays "BMI 25.0" and classifies **Normal** | The band is computed before `toFixed(1)`. Rounding first would move every boundary patient into the higher band. |
| `src/lib/currency.ts` | Header says "banker's rounding"; the implementation is `Math.round(x*100)/100`, i.e. half-up — and unreliable at the half because of IEEE-754 (`0.145 → 0.14`, `8.575 → 8.57`) | **The comment is the thing that is wrong**, not the code. Changing the rounding would move historical totals. A move to integer paise is a deliberate decision for a later phase, with the pinned cases in front of whoever makes it. |
| `src/lib/ipdAncillaryGate.ts` | An empty `urgent_priorities` list is honoured; an empty `roles` list falls back to defaults | Deliberate asymmetry: a hospital may genuinely want no auto-bypass, but must never lock every user out of the override. |
